# Smartphone capture and an on-screen card: capability audit

**Recommendation:** start with the existing camera/gallery flow, make the physical card visibly optional, and guide one private soil record at a time. A live on-screen outline is feasible later in a browser preview. It guides framing; it supplies neither a photographed reference nor physical scale, color calibration, spectra or verified instrument pairing. Never draw a fake reference card into evidence bytes.

The source already accepts missing cards. `docs/SPEC.md:118` says cardless submissions are uncalibrated; `pipeline/qa.py:580–599` records a passing card-detection check with score zero when no patches exist, and `tests/test_qa.py:205–211` has a passing sharp uncalibrated fixture. No new permission, provenance tier or relaxed QA is needed to stop presenting printing as a prerequisite. `card/CARD_SPEC.md:19` also says the printed patch values are digital targets, not spectrophotometric calibration. LIB-2 optical summaries remain uncalibrated even with a detected card.

The current browser has JPEG file inputs with `capture="environment"`. Its `camera-guide` is a static CSS illustration, not a live view (`App.tsx:117–160`, `styles.css:199–225`). The installed Capacitor Camera 8.2.4 path uses `takePhoto`; GSIP asks for no editing, resizing or gallery save, reads JPEG bytes, applies the 12 MiB limit and deletes the plugin temporary result (`platform/camera.ts`). Native saved-photo selection uses a file input. The Android permission policy explicitly removes CAMERA, media/storage and microphone permissions (`scripts/app_permissions.py:61–81`).

For browser controls, the Image Capture specification describes optional exposure, focus, white balance and torch capabilities. Still-photo fill flash is a different capability from continuous torch. Query the actual track/photo capabilities and handle rejected constraints; a recognized constraint or a successful request is not evidence of calibrated sensor behavior. Do not require these controls. The standardized photo settings provide no portable RAW/DNG switch. [W3C Image Capture](https://www.w3.org/TR/image-capture/)

An ordinary video-to-canvas snapshot is a video frame, potentially lower resolution or processed differently from a still photo. Where supported, `ImageCapture.takePhoto` can use still-image capability; retain a tested fallback. If a live guide is added, capture only the camera image, not the surrounding DOM overlay, and test rotation, mirroring and `object-fit` crop alignment. [Chrome Image Capture](https://developer.chrome.com/blog/imagecapture/), [HTML canvas drawing](https://html.spec.whatwg.org/multipage/canvas.html#dom-context-2d-drawimage)

A small staged proposal:

1. **Phone-first optional-card UX, existing capture mechanisms.** “New soil record → photos A/B → details → review → save privately.” Offer separate camera and saved-photo actions, optional physical-card help, clear retake/cancel, and no print-first barrier. Generate namespace/sample IDs through the existing flow; hide UUIDs. A node is a record namespace/sample grouping, not a federated peer. Preserve A+B, JPEG/size checks, account/rights/queue fences and private/unverified status. Unknown depth or making depth optional is a separate schema choice; do not invent zero depth or silently change validation.
2. **Browser live guide, optional enhancement.** Add an explicitly started rear-camera preview with a plain soil framing outline, accessible shutter/retake and the existing picker fallback. Request no audio. Hide unsupported controls; distinguish torch from flash. Stop every track on cancel, completed capture/review, route change, page hide, account change or lost admission. An unused late permission result must be stopped too. Keep native Android’s current permission policy unchanged; reusing this live route inside a native WebView is not included.
3. **Physical-device qualification before broad support claims.** Run the matrix below and record pass/fallback/unsupported by browser/device. Only consider custom native preview or RAW if measured browser gaps justify another reviewed package. This research selects no native dependency or service.

New custom Swift/Kotlin camera code would also require an explicit exception to the repository's TypeScript/Python source rule. A native embedded Android camera would need an approved change to the present CAMERA-permission prohibition; neither exception is needed for Stage 1 or a browser-only Stage 2.

The device matrix should include at least a recent and older iPhone in Safari and installed PWA, a supported Pixel/Android Chrome phone, and a lower-memory Android phone with a vendor camera/gallery implementation. Include portrait/landscape and rear/front selection. Test actual devices; emulation does not prove camera, picker, HEIC or memory behavior.

| Scenario | Required observation |
| --- | --- |
| Fresh camera and saved gallery | JPEG succeeds; cancellation changes nothing. Test HEIC/HEIF, PNG and cloud-backed files explicitly. A MIME accept hint is not a universal transcoding guarantee; unsupported formats receive a useful message. |
| Large images and low memory | Near/over 12 MiB, very high pixel count, repeated retakes and interrupted reads do not crash or lose an older valid draft; release previews/temporary files. |
| Orientation and preview | All EXIF orientations, portrait/landscape, camera switching and cropped preview: stored image and guides remain aligned, and no overlay pixels enter evidence. |
| Permission/device failures | First grant, denial, persistent denial, no camera, busy camera, missing APIs and rejected constraints retain a usable gallery/system-camera fallback without false success. |
| Lifecycle and ownership | Background/lock/reopen, navigation, late permission grant, sign-out/switch and withdrawal stop streams and prevent stale photos or writes from joining another account. |
| Offline/retry | Previously loaded UI and private drafts behave honestly through reload/network loss; show “on this device,” not a server receipt. Current pilot requires fresh admission before queueing/sending, so do not promise fully offline new hosted intake. Preserve exact IDs/bytes and retry/clear fences on reconnection. |

Privacy acceptance: no camera start on closed/default/rights pages; no microphone; no streaming upload or frame telemetry; only explicitly reviewed photos enter the existing private queue. Keep device IDs, capability fingerprints, images and coordinates out of logs. File selection should expose only chosen media; Android’s system photo picker documents this model. Do not add its optional Google Play backport/service to GSIP. [Android photo picker](https://developer.android.com/training/data-storage/shared/photo-picker)

`includeMetadata:false` is not proof that JPEG bytes contain no EXIF. Retain the current server sanitization and private metadata controls. Saved originals and phone/cloud gallery copies remain outside GSIP deletion control. Stream/permission tests and usable rights/account cleanup remain release criteria. No physical-device or new camera tests were run in this research; the source fixture above was inspected, not re-executed.
