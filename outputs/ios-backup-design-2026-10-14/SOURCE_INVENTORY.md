## Transaction, concurrency, rights and error invariants to preserve

- clearQueue is one readwrite transaction across ALL six stores: count submissions, increment persistent revision, persist disabled reminder with epoch+1/cleanupPending/cycleOpen false/consumed false, clear submissions/drafts/libraryDraft/namespaces, then tx.done (queue.ts:79–117). queueState and syncReminder intentionally survive as fences. Clearing both would weaken anti-resurrection/OS cleanup.
- saveDraftPhoto/saveLibraryDraft/putIfCurrent combine the generation check with the write in one transaction; putIfCurrent additionally checks existing record unless explicit first insertion. A late drain cannot reinsert a removed or discarded record. clearDraftPhotos clears draft/library plus increments persistent and fast generation; clearLibraryDraft increments persistent revision; discard-held/conflicts transactionally advances revision and removes only matching records. First-owner bind is serialized transactionally even without Web Locks (queue.ts:125–187,254–359).
- Sync drain has cross-tab gsip-sync ifAvailable lock, falls back to current idempotent behavior when unsupported. It takes both fast generation and persistent revision, checks before every checkpoint/write/removal and before subsequent records (sync.ts:59–181). Do not hold a transaction open over network calls. Every final promise must mean committed durability, not an in-memory cache assignment.
- Stable IDs/bytes, staged photosFinalized checkpoint and exact original account binding survive restart, partial upload and lost replies. Original grant acceptance is offered BEFORE reconfirmation so withdrawn records are refused/dropped rather than re-granted (supabase.ts:235–415, especially293–321). Library closure pauses; immutable conflicts hold; unknown failures back off and dead-letter after5; confirmed withdrawal drops, account change holds. Do not collapse these states (sync.ts:119–179).
- Confirmed rights outcome requested/already_open/no_account clears local queue; uncertain/failed remote request preserves local bytes. Reminder disable/fence precedes request and does not await native cleanup (YourData.tsx:98–142). Existing delete-account request does global signout; never create account to delete it (supabase.ts:435–503).
- Reminder uses separate cross-context gsip-sync-reminder lock and HOLDS when unsupported (not sync's fallback). Durable epoch/owner/lifetime gates precede permission/schedule; atomic queue+revision snapshot supplies booleans only; native completion may be late and cleanupPending must survive/replay (queue.ts:436–480; syncReminder.ts:54–58,116–142,193–260,297–365,481–495). A filesystem get/read/write interface alone does not preserve read-modify-write or snapshot atomicity.
- IDB versions1–3 upgrade additively, do not invent library/reminder records or change legacy grants. Blocking upgrade closes old database connection (queue.ts:39–59). Corruption, quota/disk-full, denied file access, interrupted write/migration, concurrent clear/signout/schedule and downgrade/old-WebView reopen need explicit safe behavior. Do not treat absent/corrupt private file as fresh identity and silently upload old records.

## Exact LibraryNoCloud behavior and constraints

Installed filesystem ios/Sources/FilesystemPlugin/IONFileStructures+Converters.swift:15–23 maps LIBRARY_NO_CLOUD to .notSyncedLibrary. Every single/dual path operation resolves getFileURL before execution (FilesystemLocationResolver.swift:8–35; FilesystemPlugin.swift:200–228). Exact audited ION file filesystem/IONFilesystemLib/IONFILEManager.swift:337–368 resolves Library/NoCloud and ATTEMPTS isExcludedFromBackup=true with try? at361–365. It does NOT first create that directory, propagate failure, read back marker or return marker state. Therefore first mkdir/write may attempt setting on a nonexistent NoCloud root and swallow failure. A subsequent path resolution reattempts the ROOT marker, not each descendant; no automatic post-write/post-rename readback or assurance exists.

The exact ION write is Data.write with no atomic option or String.write atomically:false (114–133). Append uses FileHandle writes (135–157). rename uses moveItem (170–180), but shouldPerformDualPathOperation DELETES an existing destination before move (297–309): it is not an atomic replace operation. An overwrite using temp->existing-main has a loss window. copy has the same predelete behavior. No exposed compare-and-swap, exclusive-create flag, transaction, fsync or marker get/set API was found. Stat maps only name/type/size/ctime/mtime/uri (plugin IONFileStructures+Converters.swift:38–49; definitions.d.ts:398–438), no backup marker. Directory resolution includes symlink/dot containment check (exact ION manager:252–277), but raw URI path mode skips directory containment; a private adapter should use fixed, bounded relative names and an approved directory rather than accepting record-controlled raw paths.

Conclusion: the installed plugin makes a no-new-dependency TypeScript migration worth specification study, but does not by itself establish reliable backup exclusion or transactional offline durability. Do not document marker success or atomic rename merely because directory enum says NoCloud. A selected design needs proof addressing initial creation, post-write/rename behavior, marker error visibility, crash-safe commits and cross-context exclusion. If dependable marker readback/reapplication needs new native code, the TypeScript/Python exception remains Justin's separate decision. No architecture is selected here.
