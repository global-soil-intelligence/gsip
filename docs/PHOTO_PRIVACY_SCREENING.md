# Pending v4.0 dependency review: local notifications and photo privacy

**Status:** research for the proposed [SPEC §15](SPEC.md#15-pending-v40-amendment-app-readiness-and-photo-privacy), audited 2026-10-11. No dependency/model is installed or approved for deployment. Code stays MIT, data ODbL 1.0 and contributed photos CC BY-SA 4.0. Separate upstream notices apply to third-party artifacts; an open code repository alone does not license weights or training data. These candidates need a pinned artifact/digest and a complete transitive-license/runtime-size audit in their implementation PR.

## Notification candidate

`@capacitor/local-notifications` **8.3.1** is the proposed Capacitor-8-compatible candidate: **MIT**, published **2026-08-19**; npm payload **82,938 compressed bytes / 506,577 unpacked bytes**. These are package sizes, not APK/iOS incremental size, which is **unmeasured**. The [official npm version metadata](https://registry.npmjs.org/@capacitor/local-notifications/8.3.1) declares the license and size; the [published package](https://registry.npmjs.org/@capacitor/local-notifications/-/local-notifications-8.3.1.tgz) was inspected without installing it. Its Android implementation dependencies are Capacitor and AndroidX AppCompat, with no Play Services/push dependency in that manifest; final resolved dependency scanning is still mandatory.

The [official API documentation](https://capacitorjs.com/docs/apis/local-notifications) provides local scheduling and permission checks. Version 8.3 supports `isExactNotification: false`, but the audited package manifest includes `SCHEDULE_EXACT_ALARM` alongside `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED` and `WAKE_LOCK`. WP-APP-2B must remove exact-alarm permissions from the effective merged manifest, schedule inexactly, request notification permission only after opt-in and verify the built APK. Boot/wake permissions may be allowed only with a demonstrated reminder need. No background location, push service or closed SDK is proposed. Current docs can change; recheck the pinned package's actual API/manifest and measured build size before implementation.

## Publication policy and evidence still required

Justin chose **private human review with individual photo withholding**. Automatic blur is excluded; structured observation data and other eligible photos retain their normal path. Every photo stays private until the server-controlled screen has cleared its exact sanitized bytes or an authorized human has cleared a false positive. Missing/erroring screens, ambiguous detections and unsupported categories keep that photo withheld. Human review happens through a private operator CLI; no raw image, OCR text, precise location or review payload enters a public surface/log/fixture. See [SPEC §15.4](SPEC.md#154-wp-6f-every-photo-privacy-screening-pending-implementation-approval).

Actual GSIP recall/false-positive rates are **UNKNOWN**. Before public photo publication, the implementation must use synthetic/staged, permissioned material (no real contributor uploads in fixtures) to report category-level sample counts, misses, false positives, confidence intervals, runtime and unsupported cases; tune high-recall thresholds; and have Justin review the acceptance evidence. Include every shot, context outside soil/card masks, tiny/occluded faces, varied skin tones, oblique/unreadable plates and multiple scripts. No detection is not proof of anonymity. Do not log detected strings or bounding evidence publicly. Retain existing grant, QA, withdrawal, provenance, holdout and k-anonymity checks; photos and data have independent publication eligibility.

## Assumptions and gates

- This proposal schedules local reminders to fulfill the version-1 risk mitigation; App Store guideline 4.2 acceptance still needs actual reviewer assessment and signing/accounts remain Justin's actions.
- Local nearby suggestions may need public land-access/minor eligibility inputs that do not exist yet. Keep that feature disabled until eligibility can be supported; do not infer safe access from low public coverage.
- Android backup policy can be prepared/tested without accounts; iOS exclusion of current WebKit-owned stores is not established. No native-language exception or storage migration is implicitly authorized.
- Upstream license statements and dated payload metadata were verified for the named snapshots on 2026-10-11; training provenance, transitive runtime licenses/size and GSIP performance need their own implementation evidence.
- **WP-6f implementation waits for Justin's approval and merge of this specification PR.** No deployment, dependency install, migration, capture opening, service addition or license change occurs here.
