# GSIP project review — 2026-09-14

## Assessment

GSIP has a substantial Phase 1 implementation: a public information site, offline capture app, soil-prior map, reference-card tooling, database access policies, photo QA, and dataset export. It is a working development foundation, but I would not open public contribution intake until the findings below are resolved.

This review covers local branch `wp-site-public-hub` at `a581d20`. It is not a production certification. Hosted settings, current PR approvals, scheduled-job credentials, dataset publication, and real-phone operation were not verified. The July deployment handoff is historical evidence, not confirmation of present readiness.

## Findings

### 1. [P1] A partially processed submission can pass QA

**Location:** `pipeline/qa_worker.py:150–164`; `pipeline/qa.py` (`aggregate_submission_status`).

The worker decides the submission's status from whichever QA events currently exist. It does not require both mandatory shots, completion of every attached photo job, or a complete set of required checks. A corrupt shot produces no failing QA event; another good shot can therefore mark the entire submission `qa_pass`.

**Reproduced:** Using the existing worker harness with a corrupt A photo and a valid B photo produced `hostile: dead_letter`, `good: completed`, and submission status `qa_pass`. The existing test explicitly accepts this incorrect outcome.

**Impact:** An upload interrupted before its second photo can qualify prematurely. If the failed photo row exists, the export selects it too and attempts to load its nonexistent canonical image, potentially aborting the entire nightly export. If the row was never inserted, the incomplete photo set can export.

**Fix direction:** Finalize a submission only after upload completion is explicit, required shots exist, and all attached photos have completed their required checks. Keep failed or incomplete submissions out of export. Add a regression covering one good photo plus one corrupt or missing required photo.

### 2. [P1] The launch flag does not close contribution intake

**Locations:** `apps/map-web/src/App.tsx:171–173`; `apps/capture-pwa/src/supabase.ts:16–20`; `apps/site-web/src/App.tsx:6`.

`VITE_CAPTURE_LIVE=false` changes the information site's links, but the map still links directly to `/capture/`. The capture app initializes and syncs whenever a Supabase URL and public key exist. It never reads the launch flag, and the Pages build always includes it.

**Verified:** The desktop browser suite passes both the “Capture opening soon” assertion and the map-to-capture submission journey in the same configuration.

**Impact:** With working backend authentication, users can submit while the public site says capture is closed. With no configuration, they can still queue sensitive photos and exact locations locally. This does not prove hosted intake is currently enabled; it proves the flag is not an intake control.

**Fix direction:** Apply consistent closed-state behavior to the map and capture app, including startup queue sync. If intake must be closed regardless of cached clients, enforce that decision on the backend as well.

### 3. [P2] Interrupted prior jobs have no automatic recovery

**Location:** `pipeline/prior_worker.py:17–25`; `supabase/migrations/20260723044745_atomic_prior_attempt_claim.sql:8–18`.

Claiming an enrichment attempt writes `processing`. The scheduled drain selects only `pending` and `dead_letter`. A runtime termination or timeout after the claim can leave a job permanently excluded from subsequent drains; no stale-processing recovery for prior jobs exists in this checkout.

**Fix direction:** Introduce an expiring processing claim, recover expired jobs, and prevent concurrent claims of an unexpired job. Verify recovery after a simulated termination between claim and completion.

### 4. [P2] A completion-write failure makes successful photo processing unrecoverable

**Location:** `pipeline/qa_worker.py:166–179`.

The worker deletes the raw photo before recording job completion. If that final database write fails, it marks the job retryable. Every retry then tries to download the deleted raw object instead of resuming from the canonical photo and persisted results.

**Reproduced:** Injecting one HTTP 503 into the completion update produced three retry states followed by `dead_letter`, despite successful canonical promotion and sanitization.

**Fix direction:** Persist resumable processing stages or recognize already-promoted results. Make finalization and cleanup independently retryable, with a regression for failure after deletion.

### 5. [P2] Email sign-in does not preserve anonymous ownership

**Location:** `apps/capture-pwa/src/App.tsx:187–197`.

The UI invites anonymous contributors to obtain a magic link to return to their history. It always calls `signInWithOtp`, without linking the email to the current anonymous identity or transferring ownership. Signing into a different account leaves existing contributor rows and grants attached to the original user. A partially uploaded queued submission can then repeatedly fail against the new identity.

Supabase documents `updateUser` for linking an email to an anonymous user, with a separate conflict-handling flow for an existing account: [Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous).

**Fix direction:** Preserve the anonymous user ID when adding a new email identity, handle existing-account conflicts explicitly, and verify partially synced observations across an account transition. This finding is based on code and the authentication contract; it was not exercised against hosted Auth.

## Product and next milestone

The implemented product is a contribution and soil-prior mapping system. The repository explicitly defers the soil classifier and trained estimator to Phase 2; passing software tests does not establish soil-estimation accuracy or research adoption.

Keep the existing capture-to-export scope. First resolve the QA and intake findings, then the recovery and identity issues. Next run one complete controlled pilot: capture both required photos on a real phone, interrupt connectivity, reconnect, verify both photo jobs and priors, inspect a private export, and confirm the corresponding public aggregate after publication is authorized. Reconcile the historical launch checklist against current hosted state before enabling public intake.
